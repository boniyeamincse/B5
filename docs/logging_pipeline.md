# B5 WAF — Logging Pipeline to OpenSearch/Elasticsearch

**Version:** 1.0  
**Last Updated:** 2026-05-03  
**Related:** [architecture_overview.md](architecture_overview.md)

---

## 1. Overview

Every time B5 detects a security violation, rate limit breach, or notable request, it generates a **security event**. These events are structured JSON documents shipped to **OpenSearch** (or Elasticsearch) for storage, search, and analytics.

The logging pipeline is designed around two principles:

1. **Non-blocking**: Logging must never slow down or block request processing. If the log store is temporarily unavailable, requests must still be handled.
2. **Structured data**: Every event uses a consistent JSON schema so it can be searched, filtered, and aggregated without guesswork.

---

## 2. What Events Are Generated

B5 generates security events for the following triggers:

| Trigger | Event Type | Severity |
|---------|-----------|---------|
| WAF rule match (SQLi, XSS, etc.) | `waf_violation` | Depends on rule severity |
| Rate limit exceeded | `rate_limit` | `medium` |
| IP blocklist match | `ip_blocked` | `high` |
| IP reputation threshold exceeded | `ip_reputation` | `high` |
| Login brute-force threshold exceeded | `brute_force` | `critical` |
| Malformed HTTP request | `malformed_request` | `low` |
| Large request body rejected | `payload_too_large` | `medium` |
| Disallowed HTTP method | `method_not_allowed` | `low` |

In **blocking mode**, only blocked requests are logged as security events. In **logging mode**, all detected violations are logged even if the request was allowed through.

## 3. Security Event JSON Schema

Every security event written to OpenSearch follows this structure:

```json
{
  "timestamp":         "2026-05-03T10:22:01.452Z",
  "request_id":        "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "application_id":    3,
  "application_name":  "My E-commerce Site",
  "client_ip":         "203.0.113.42",
  "client_country":    "CN",
  "method":            "GET",
  "host":              "shop.example.com",
  "path":              "/products",
  "query":             "id=1'+UNION+SELECT+username,password+FROM+users--",
  "user_agent":        "curl/7.88.1",
  "referer":           null,
  "rule_id":           "sqli-001",
  "rule_name":         "SQLi Union Select",
  "attack_type":       "SQL Injection",
  "matched_pattern":   "(?i)union[\\s\\+]+select",
  "matched_value":     "1' UNION SELECT username,password FROM users--",
  "action":            "blocked",
  "severity":          "critical",
  "risk_score":        92,
  "policy_id":         1,
  "policy_mode":       "blocking",
  "backend_status":    null,
  "response_time_ms":  null,
  "bytes_sent":        412
}
```

**Field reference:**

| Field | Type | Description |
|-------|------|-------------|
| `timestamp` | ISO 8601 UTC | When the event occurred |
| `request_id` | UUID | Unique identifier for this specific request, generated by Lua |
| `application_id` | integer | ID of the protected application in PostgreSQL |
| `application_name` | string | Human-readable application name |
| `client_ip` | string | Original client IP (from `X-Forwarded-For` or `remote_addr`) |
| `client_country` | string | 2-letter country code (from GeoIP lookup, if available) |
| `method` | string | HTTP method: GET, POST, PUT, DELETE, etc. |
| `host` | string | `Host` header value |
| `path` | string | Request path without query string |
| `query` | string | Raw query string (may be null) |
| `user_agent` | string | `User-Agent` header value |
| `referer` | string | `Referer` header value (may be null) |
| `rule_id` | string | ID of the matched rule |
| `rule_name` | string | Human-readable rule name |
| `attack_type` | string | Category: `SQL Injection`, `XSS`, `Path Traversal`, etc. |
| `matched_pattern` | string | The regex that triggered the match |
| `matched_value` | string | The decoded request value that matched (for investigation) |
| `action` | string | `blocked`, `logged`, `allowed`, `rate_limited` |
| `severity` | string | `info`, `low`, `medium`, `high`, `critical` |
| `risk_score` | integer | 0–100 composite risk score |
| `policy_id` | integer | ID of the active policy |
| `policy_mode` | string | `blocking`, `logging`, or `learning` |
| `backend_status` | integer | HTTP status returned by backend (null if request was blocked) |
| `response_time_ms` | integer | Backend response time in ms (null if blocked) |
| `bytes_sent` | integer | Response bytes sent to client |

## 4. How Events Are Sent to OpenSearch

### Option A: Direct from Lua (MVP — simple)

In the Nginx `log_by_lua_file` phase, the Lua script writes the event JSON directly to OpenSearch using an HTTP POST:

```lua
-- log.lua (runs after response is sent to client)
local http  = require "resty.http"
local cjson = require "cjson"

local event = {
    timestamp    = ngx.utctime(),
    request_id   = ngx.var.request_id,
    client_ip    = ngx.var.remote_addr,
    method       = ngx.req.get_method(),
    path         = ngx.var.uri,
    attack_type  = ngx.ctx.attack_type,
    action       = ngx.ctx.action,
    severity     = ngx.ctx.severity,
    risk_score   = ngx.ctx.risk_score,
}

local httpc = http.new()
httpc:request_uri("http://b5-opensearch:9200/b5-events-" .. date_suffix .. "/_doc", {
    method  = "POST",
    body    = cjson.encode(event),
    headers = { ["Content-Type"] = "application/json" },
})
```

The `log` phase runs **after** the response has been sent to the client, so the HTTP POST to OpenSearch does not add latency visible to the end user.

> **Note:** If OpenSearch is unreachable, the log is dropped silently. For production, use Option B or add a retry buffer.

### Option B: Via a Log Shipper (Production)

For higher reliability and throughput, OpenResty writes events to a local file or stdout, and a dedicated log shipper (e.g., **Filebeat**, **Logstash**, **Vector**) reads and forwards them to OpenSearch:

```
OpenResty/Lua
  └─► writes JSON events to /var/log/b5/security_events.log
        └─► Filebeat reads the file
              └─► ships to OpenSearch (with retry on failure)
```

This decouples logging from request processing entirely: even if OpenSearch is down for minutes, events are buffered on disk and replayed when connectivity resumes.

## 5. Why OpenSearch / Elasticsearch?

| Requirement | How OpenSearch Handles It |
|------------|--------------------------|
| Full-text search over millions of log records | Inverted index for instant `query_string` searches |
| Filtering by IP, attack type, date range | Structured field indexing, fast range queries |
| Aggregations (top attackers, hourly trends) | Elasticsearch aggregation API |
| Real-time ingest | REST API accepts documents immediately; no batch window |
| Retention management | Index Lifecycle Management (ILM) policies |
| Scalability | Horizontally scalable — add nodes to handle more data |

## 6. OpenSearch Index Strategy

B5 uses **daily rolling indices** for security events:

```
Index name pattern: b5-events-YYYY.MM.DD

Examples:
  b5-events-2026.05.01
  b5-events-2026.05.02
  b5-events-2026.05.03
```

Daily indices allow:
- Easy deletion of old data (just delete old indices).
- Per-day query routing (faster searches when date range is specified).
- Independent shard sizing based on daily event volume.

### Index Mapping (Template)

```json
{
  "index_patterns": ["b5-events-*"],
  "mappings": {
    "properties": {
      "timestamp":       { "type": "date" },
      "request_id":      { "type": "keyword" },
      "application_id":  { "type": "integer" },
      "client_ip":       { "type": "ip" },
      "method":          { "type": "keyword" },
      "host":            { "type": "keyword" },
      "path":            { "type": "keyword" },
      "query":           { "type": "text" },
      "attack_type":     { "type": "keyword" },
      "action":          { "type": "keyword" },
      "severity":        { "type": "keyword" },
      "risk_score":      { "type": "integer" },
      "policy_mode":     { "type": "keyword" },
      "user_agent":      { "type": "text" }
    }
  }
}
```

`keyword` fields are used for exact-match filtering and aggregations. `text` fields are full-text searchable.

## 7. Retention Policy

| Retention Period | Configuration |
|----------------|---------------|
| Hot (recent 7 days) | Full index, all shards in memory |
| Warm (7–30 days) | Merged shards, slower queries acceptable |
| Cold (30–90 days) | Compressed, read-only |
| Delete (> 90 days) | Indices deleted automatically by ILM |

This is configured via OpenSearch Index Lifecycle Management (ILM). Adjust retention based on storage capacity and compliance requirements.

## 8. Risk Score Calculation

The `risk_score` field (0–100) is a composite score calculated by `access.lua` at the time of the event:

| Factor | Points |
|--------|--------|
| Rule severity = `critical` | +40 |
| Rule severity = `high` | +25 |
| Rule severity = `medium` | +15 |
| Rule severity = `low` | +5 |
| IP reputation score (scaled) | 0–30 |
| Rate limit violation | +10 |
| Multiple rule matches | +10 |
| Repeated offender (seen in Redis) | +10 |

**Example:**

```
Rule match (critical SQLi) → +40
IP reputation score 70/100 → +21 (70 * 0.3)
Repeated offender flag     → +10
────────────────────────────────
Risk Score = 71
```

Scores ≥ 80 trigger auto-block in blocking mode and high-priority alerts.

## 9. Querying Events from the Dashboard

The FastAPI control plane queries OpenSearch using its search API. Example query for the dashboard events page:

```json
POST /b5-events-*/_search
{
  "query": {
    "bool": {
      "filter": [
        { "term":  { "attack_type": "SQL Injection" } },
        { "term":  { "action": "blocked" } },
        { "range": { "timestamp": { "gte": "2026-05-01", "lte": "2026-05-03" } } }
      ]
    }
  },
  "sort": [{ "timestamp": "desc" }],
  "size": 50
}
```

Aggregation query for the "Top Attacking IPs" dashboard widget:

```json
POST /b5-events-*/_search
{
  "size": 0,
  "aggs": {
    "top_ips": {
      "terms": { "field": "client_ip", "size": 10 }
    }
  }
}
```
